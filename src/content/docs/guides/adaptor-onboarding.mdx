This is the recommended path for a new **adaptor**: an organisation deploying Blue Dots for a district, state or domain. The steps are the same for every network, such as jobs (Blue Dot) or education (Yellow Dot). It assumes you have read [Blue Dots as a DPG](/overview/blue-dots-as-a-dpg/).

## Step 1: Stand up Signals

Start with the network-aware backend. Follow [Signals DPG Setup](/guides/installation/local-setup/signals-dpg/). At the end you should have the Signals API and UI running against local Postgres + Redis.

## Step 2: Define your network and domains

Decide the **network** you participate in and the **domains** your instance serves. For example, the jobs network `blue_dot` has the domains `seeker` and `provider`, and the education network (Yellow Dot) has a student domain and a tutor/counsellor domain. See [Networks, Domains and Instances](/core-concepts/networks-domains-instances/) for every network. Because the model is [schema-driven](/core-concepts/technical/schema-driven-model/), you express these as schemas and `SERVED_DOMAINS` config, not code. Define your item types (e.g. `profile_1.0`) up front.

## Step 3: Add the Aggregator DPG

When you are ready to onboard many partner organisations, add the [Aggregator DPG](/guides/installation/local-setup/aggregator-dpg/). Configure it to write participant profiles and listings into your Signals instance through the bulk-create paths, signing in with a [Keycloak service account](/core-concepts/architecture/identity-and-auth/):

```http
authorization: Bearer <client-credentials token>
x-acting-org-id: <the organisation you act as>
```

Register a confidential Keycloak client whose **client id equals your
organisation's `slug`**, then add it to `KEYCLOAK_SERVICE_CLIENT_IDS` on the
Signals API. The list is empty by default, so a new DPG is refused until it is listed. See
[Keycloak Setup](/guides/keycloak-setup/).

## Step 4: Add capture channels

- **Web:** the schema-driven Signals UI and the Aggregator portal.
- **Voice AI:** low-cost capture by phone call in the local language. A voice DPG connects the same way an aggregator does (Keycloak service account and bulk create). Ready-made prompt sets for the jobs network are published as DPGs; see [AI Voice Agent Prompts](/guides/voice-ai-prompts/).

On the assisted route, pick the intake method per campaign: offline camp, bulk upload, outbound campaign or inbound QR campaign. All four ship ready-made; see [The Dot Lifecycle](/core-concepts/blue-dot-lifecycle/#3-data-collection-assisted-route).

## Step 5: Integrate notifications

Wire **SMTP** (email) and an **SMS** provider for OTP, confirmations and match notifications. Mailpit covers email locally.

## Step 5b: Make it yours

Branding, operational settings, dashboards and a public landing page are configuration and presentation layers. None of them needs changes to the Signals or Aggregator code. See [Customisation & Branding](/guides/customisation/).

## Step 6: Pilot and measure

Run a bounded pilot in one district and track before and after metrics. The jobs pilots in Ghaziabad and Dharwad tracked jobs found, time to find a match, cost per interaction and conversion; other networks pick measures for their own sector. See [Pilots](/explore/pilots/).

## Onboarding checklist

- [ ] Signals API + UI running, migrations applied.
- [ ] Network schema and `SERVED_DOMAINS` defined; item types registered.
- [ ] Keycloak realm imported; admin user created.
- [ ] Aggregator DPG deployed.
- [ ] Service client registered (id = org `slug`) and listed in `KEYCLOAK_SERVICE_CLIENT_IDS`.
- [ ] SMTP + SMS providers connected.
- [ ] S3 bucket + credentials provisioned for bulk upload.
- [ ] Branding applied (`brand.json`, UI theme, Keycloak login theme).
- [ ] Route in (assisted / self) and intake method chosen per campaign.
- [ ] Pilot scope and impact metrics agreed.
