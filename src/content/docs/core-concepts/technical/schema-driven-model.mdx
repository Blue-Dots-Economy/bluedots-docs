Blue Dots is **schema-driven** end to end. Schemas define what an instance stores, exchanges and renders. A new network, domain or form ships by adding or editing schema files.

## Three kinds of schema

- **Network schema (`network.json`)** — defines a network (for example `blue_dot` for jobs, or the Yellow Dot education network): its domains, item types, actions and events.
- **Item schemas (`item_type`)** — versioned types such as `profile_1.0`. An item's `item_type` always points at one of these; freeform records are not allowed.
- **Form schemas** — JSON schemas that drive the UI. The Signals UI renders forms and cards from item schemas; the Aggregator portal uses **RJSF** (React JSON Schema Form) so non-engineers can evolve registration and profile forms.

## Why schema-first

1. **Interoperability.** Two instances on the same network load the same `network.json`, so they agree on structure. That shared structure is what lets one instance search another.
2. **Evolvability.** Versioned `item_type`s (e.g. `profile_1.0` → `profile_1.1`) let the model change without breaking peers.
3. **No-code domain changes.** Product and program teams can add fields or new forms by editing schemas/config, not code.

## Choosing a network

Each network is a folder under `examples/schemas/` in the Signals DPG repository. Today there are four: `blue_dot` (jobs), `yellow_dot` (education), `purple_dot` (persons with disabilities) and `orange_dot` (tourism). The list of networks, their domains and their status is on [Networks, Domains & Instances](/core-concepts/networks-domains-instances/).

A network folder holds:

- `network.json`: the network id, its domains, item types and actions.
- `consent.json`: the consent text participants accept (terms, privacy, profile and action consent).
- `messages.properties`: optional overrides for the email copy.
- Brand sub-folders: a brand is a UI and copy skin over the network. It does not change the schema.

A deployment runs one network. It chooses it with settings, not code: which `network.json` to load, which domains to serve, and which network id the UI shows. The setup guides list the exact variables: [Signals DPG Setup](/guides/installation/local-setup/signals-dpg/#choose-a-network) for local runs and [AWS Infrastructure Setup](/guides/installation/cloud-setup/aws/infrastructure/#choose-the-network) for a cluster.

The same `profile_1.0` has different fields on each network. A Blue Dot (jobs) seeker profile and a Yellow Dot student profile are both `profile_1.0`, but each network's `network.json` defines its own fields.

## Backend-owned fields

Some fields are authoritative and server-generated; clients must never set them:

- `item_instance_url` — where an item lives.
- `item_schema_url` — the schema it conforms to.

## Configuration discipline

Schema-driven design is paired with strict configuration discipline:

- **All env vars are declared in one place** (the Signals `packages/config` Zod schema; the Aggregator config loader). Ad-hoc `process.env` reads are not allowed.
- In Signals, adding an env var means changing **two places together**: the Zod schema *and* `turbo.json`'s `globalPassThroughEnv`, or the value won't reach filtered tasks.
- Per-environment values are set as environment variables: in `.env` files locally, and through the Helm values in `bluedots-automation` on a cluster.
