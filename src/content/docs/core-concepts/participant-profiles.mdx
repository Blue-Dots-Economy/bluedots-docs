Each domain defines who can publish a blue dot, so that people and organisations nearby can find them, and which fields each participant type fills in. This page shows the Blue Dot (jobs) domain in full, because it is the live domain used in the pilots. The Yellow, Purple and Orange domains follow the same pattern with their own fields; see [Other domains](#other-domains) below.

In the jobs domain, three participant types are already worked out. An adaptor does **not** need to design them from scratch.

| Type | Who they are | `domains` `id` | Item schema |
|---|---|---|---|
| **Job Seeker** | A person looking for work | `seeker` | `profile_1.0` |
| **Job Provider** | An employer posting a vacancy | `provider` | `job_posting_1.0` |
| **Service Provider** | An organisation offering support to job seekers: training, counselling, assessment or placement help | `service_provider` | `profile_1.0` |

`seeker` and `provider` are declared in the [jobs minimum standard](https://github.com/Blue-Dots-Economy/signals-dpg/blob/main/examples/schemas/blue_dot/network.json), the list of fields every blue dot in that domain must have. The code lists participant types in the `domains` field of `network.json` (and calls a domain a *network*). `service_provider` comes from the deployed pilot schemas; the example file does not include it.

## One structure, three fillings

Every participant type follows the same simple **three-part structure**, so profiles stay consistent and easy to extend:

- **Who I am** — identity and contact details.
- **What I want** — the need or opportunity being sought.
- **What I have** — location, capacity, skills, or credentials on offer.

Only the *details* within each part differ by participant type. An adaptor can adjust or add fields as needed **without rebuilding the structure itself**.

## The three parts, in real fields

The shipped schemas are laid out in these three parts. Here is each part with its real field names:

### Job Seeker

Participant type `seeker`, item schema `profile_1.0`.

| Part | Fields |
|---|---|
| **Who I am** | `name`, `age`, `gender`, `phone`, `location`, `languageSpoken` |
| **What I want** | `natureOfJobsInterestedIn`, `nameOfJobRolesInterestedIn`, `otherHelpNeeded` |
| **What I have** | `workExperience`, `nameOfLastRoleHeld`, `educationCategory`, `itiTrade`, `itiInstitute`, `polytechnicDiploma`, `certificationDetails` |

Required at minimum: `name`, `location`, `age`, `phone`.

:::tip[`otherHelpNeeded` records needs beyond a job]
This one field is where job seekers mention other needs, such as counselling, skilling, capital, proof of skill or interview preparation. See [What We're Learning](/explore/learnings/#2-the-conversations-are-showing-many-different-needs).
:::

### Job Provider

Participant type `provider`, item schema `job_posting_1.0`.

| Part | Fields |
|---|---|
| **Who I am** | `jobProviderName`, `jobProviderLocation`, `hiringManagerName`, `hiringManagerPhoneNumber`, `hiringManagerEmail` |
| **What I want** | `candidateExperienceType`, `workExperienceYears`, `lastRoleHeld`, the `minQualification*` family |
| **What I have** | `role`, `positions`, `natureOfJob`, `salaryMin`/`salaryMax`, `stipendMin`/`stipendMax`, `taskRateMin`/`taskRateMax` |

A job provider's *What I have* is the job itself: the role, how many openings, and on what terms.

### Service Provider

Participant type `service_provider`, item schema `profile_1.0`. These fields are from the deployed pilot schemas.

| Part | Fields |
|---|---|
| **Who I am** | `serviceProviderName`, `organisationType`, `contactPersonName`, `contactPhoneNumber`, `contactEmail`, `location` |
| **What I want** | `participantTypesServed`, `needsAddressed` |
| **What I have** | `servicesOffered`, `serviceMode`, `coverageArea`, `capacityPerMonth`, `costModel`, `accreditation`, `languagesSupported` |

## Other domains

The other defined domains use the same three parts. The fields below are shown by their form labels.

| Domain and participant type | Who I am | What I want | What I have |
|---|---|---|---|
| Yellow Dot (education): student | Full Name, Phone Number, Email Address, Location | Service Looking For (for example Subject Tutoring or Career Counseling), Grade, Academic Stream | None |
| Yellow Dot (education): tutor or counsellor | Full Name, Phone Number, Email Address, Location | Grade Bands Served, Academic Streams Served | Service Offered, Coverage Radius (km) |
| Purple Dot (persons with disabilities): `seeker` | Name, Age, Gender, Mobile, Address | Looking For (for example Assistive Devices or Employment Opportunities), Details | Disability, Disability %, Documents, Qualification |
| Purple Dot (persons with disabilities): `provider` | Contact Name, Phone, Organisation, Category, Organisation Address | Disabilities Served | Services Offered, Service Cities, Service Details |
| Orange Dot (tourism): `practitioner` | Provider Name, Contact Phone, Area | None. Listings are public and have no actions. | Product Name, Category, Description, Services Provided, Languages, Pricing, Verified By |

The minimum standards for these domains are in the Signals DPG repository: [Yellow](https://github.com/Blue-Dots-Economy/signals-dpg/blob/main/examples/schemas/yellow_dot/network.json), [Purple](https://github.com/Blue-Dots-Economy/signals-dpg/blob/main/examples/schemas/purple_dot/network.json) and [Orange](https://github.com/Blue-Dots-Economy/signals-dpg/blob/main/examples/schemas/orange_dot/network.json). Pink, Green and Brown have no minimum standard published yet.

## Extending a profile

Because registration and profile forms are **schema-driven**, adding or changing a field is a schema edit — no application code change:

1. Edit the item schema in the domain config (`item_schemas` for the participant type).
2. Add the new field to the participant type's `x-form-layout` sections so it renders in the right place.
3. If it should show on the participant card, add it to `card.default_fields`.

See [Schema-Driven Model](/core-concepts/technical/schema-driven-model/) for the mechanism and [Configuration](/guides/configuration/) for where each file lives.

:::caution[Two fields are never yours to set]
`item_instance_url` and `item_schema_url` are generated by the backend during item creation. See [Anatomy of a signal](/core-concepts/signals/#anatomy-of-a-signal).
:::
